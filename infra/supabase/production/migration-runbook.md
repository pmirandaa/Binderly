# Production migration runbook

How Binderly applies schema migrations to the **production** Supabase
Postgres, and how to roll back when one goes wrong.

---

## How migrations apply (the happy path)

1. A PR adds a new `packages/db/src/migrations/NNNN_*.sql` (generated by
   `pnpm db:generate` from the Drizzle schema) and merges to `main`.
2. `.github/workflows/deploy-db.yml` triggers on that path, runs
   `pnpm install`, then `pnpm db:migrate` with `DATABASE_URL` =
   `secrets.PROD_DATABASE_URL`.
3. `packages/db/scripts/migrate.ts` runs the Drizzle `postgres-js` migrator,
   which:
   - reads the ordered `*.sql` files + `meta/_journal.json`,
   - checks the `drizzle.__drizzle_migrations` journal table on the prod DB,
   - applies **only** migrations not already recorded there,
   - records each newly-applied migration in the journal.

### Idempotency + safety guarantees

- **Idempotent:** re-running the workflow (or re-merging) is a no-op for
  already-applied migrations — the journal table is the gate.
- **Non-destructive:** the workflow uses the forward-only migrator. It does
  **not** run `supabase db reset`, `drizzle-kit push`, or any drop/truncate.
  A migration only does what its `.sql` says.
- **No partial commits:** each migration file runs in the migrator's
  transaction; a failing statement aborts that migration and the workflow
  exits non-zero (the journal is not advanced past the failure).

## Connection string

`PROD_DATABASE_URL` should be the project's Postgres connection string from
the Supabase dashboard (Project Settings → Database → Connection string).
Prefer the **session pooler** (port `5432`) or **direct** connection for
migrations — *not* the transaction pooler (port `6543`), which doesn't
support the session-level statements some DDL/migration tooling issues.

```
postgresql://postgres:<DB_PASSWORD>@db.<PROJECT_REF>.supabase.co:5432/postgres?sslmode=require
```

Store it as a GitHub Actions secret (see `infra/DEPLOYMENT_SECRETS.md`).

## Staging-first (strongly recommended)

Per `rules/11-deployment.md` ("test on a staging Supabase project first"):

1. Create a **staging** Supabase project mirroring production.
2. Point a `STAGING_DATABASE_URL` at it and run the migrate flow there first
   (manually: `DATABASE_URL=<staging> pnpm db:migrate`, or a staging variant
   of the workflow via `workflow_dispatch`).
3. Smoke-test the app against staging, then let the merge-to-`main` apply the
   same migrations to production.

## Rollback

Drizzle migrations are **forward-only** — there is no auto-generated `down`.
Pick the cheapest safe option for the failure:

1. **Forward-fix (preferred for additive mistakes).** Write a new migration
   that corrects the problem (e.g. drop the bad column, fix the constraint)
   and merge it. Keeps the journal linear and auditable.
2. **Hand-authored down migration.** For a known-reversible change, author a
   compensating `.sql` and apply it via `DATABASE_URL=<prod> pnpm db:migrate`
   after adding it as the next migration. Document the reversal in the PR.
3. **Point-in-Time Recovery (data-loss incidents).** Supabase Pro supports
   PITR. Restore the project to a timestamp just before the bad migration
   from the dashboard (Database → Backups). This is the heaviest option —
   coordinate with Pablo; it reverts *data*, not just schema.

After any rollback, reconcile `meta/_journal.json` / the journal table state
with what's actually on the DB before the next `db:migrate`.

## Ordering vs app deploys

`rules/11-deployment.md`: **migrations run before app deploy.** At go-live,
sequence so `deploy-db` completes before `deploy-web` / `deploy-fly` for a
release that includes a schema change. Options:

- Merge the migration PR first, let `deploy-db` finish, then merge the app PR.
- Or trigger the three workflows in order via `workflow_dispatch`.

A combined release-orchestration workflow (db → web/fly fan-out) is a
sensible future enhancement; not built in this scaffolding pass.

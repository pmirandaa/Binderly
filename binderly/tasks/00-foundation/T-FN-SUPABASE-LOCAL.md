## Goal
Stand up a local Supabase project via `supabase init` so that auth,
postgres-as-supabase, edge functions, and storage all work locally.
Coexist with the Docker compose stack from T-FN-DOCKER (which provides our
*own* Postgres for the data-pipeline workflows; the Supabase CLI brings
its own Postgres for the app side — keep them on different ports and
clearly documented).

## Deliverables

- `infra/supabase/config.toml` — generated by `supabase init`, edited:
  - `[api] port = 54321`
  - `[db] port = 54322`
  - `[studio] port = 54323`
  - `[inbucket] port = 54324`
  - Auth providers configured (Google, Apple, Discord, magic link) with
    placeholder values and clear comments where to fill real client IDs.
- `infra/supabase/seed.sql` — empty placeholder, ready for data-layer
  tasks to populate fixtures.
- `infra/supabase/README.md` — how to start the local Supabase
  (`supabase start`), how to apply migrations (deferred to
  T-FN-DB-MIGRATIONS), how to reset.
- `package.json` (root) — add scripts:
  - `db:start` → `supabase start --workdir infra/supabase`
  - `db:stop` → `supabase stop --workdir infra/supabase`
  - `db:reset` → `supabase db reset --workdir infra/supabase`
- Root `.env.example` updated with the Supabase URL, anon key, service
  role key (from `supabase status` output, well-known dev defaults).

## Acceptance criteria

- [ ] `pnpm db:start` brings up Supabase locally.
- [ ] `pnpm db:stop` shuts it down.
- [ ] Supabase Studio accessible at `localhost:54323`.
- [ ] Auth providers visible (with placeholder configs) in Studio.
- [ ] Local Supabase Postgres on 54322 does NOT conflict with the
      docker-compose Postgres on 5433.
- [ ] `.env.example` documents both Postgres endpoints clearly: which is
      which, what to use when.
- [ ] No file modified outside `infra/supabase/`, root `package.json`,
      `.env.example`, and a `README` cross-link.

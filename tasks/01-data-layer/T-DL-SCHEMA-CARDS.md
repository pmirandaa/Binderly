## Goal
Define the Drizzle schemas for `set`, `card`, and `printing` tables
exactly as specified in `context/data-model.md`. Generate the migration.
Add fixture builders for tests in subsequent tasks.

## Deliverables

- `packages/db/src/schema/sets.ts` — Drizzle table for `set` matching the
  spec column-for-column. Indexes per spec.
- `packages/db/src/schema/cards.ts` — Drizzle table for `card` matching
  the spec. FK to sets.
- `packages/db/src/schema/printings.ts` — Drizzle table for `printing`
  matching the spec. FK to cards. Partial index on
  `include_in_master_set`.
- `packages/db/src/schema/index.ts` — re-export the new tables.
- `packages/db/src/migrations/0001_catalog_tables.sql` — generated SQL
  for these three tables (via `pnpm db:generate`).
- `packages/db/src/fixtures/cards.ts` — typed fixture builders for tests:
  `makeSet({...overrides})`, `makeCard({...overrides})`,
  `makePrinting({...overrides})`. Defaults are deterministic and
  realistic (e.g., a Base Set Charizard with sensible values).
- `packages/db/src/fixtures/cards.test.ts` — verifies fixtures round-trip
  through the schema (insert + select equality).

## Acceptance criteria

- [ ] All three tables match `context/data-model.md` exactly.
- [ ] Migration applies cleanly to a fresh local DB.
- [ ] Indexes from spec exist (`set` release-date index, `card` set+number
      and trigram name index, `printing` card_id and partial
      master-set index).
- [ ] Fixture round-trip test passes against the local DB.
- [ ] Field types are correct: `release_date` is `date`, `number` is
      `text` (preserves leading zeros and `TG01`-style values),
      `variant_flags` is `text[]` not `jsonb`.
- [ ] `printing.variant_key` and `card.canonical_key` are unique
      constraints, not just unique indexes — they must reject inserts.
- [ ] No file modified outside `packages/db/src/schema/`,
      `packages/db/src/migrations/`, `packages/db/src/fixtures/`,
      `packages/db/src/index.ts`.
- [ ] No application code yet (no queries, no API), only schema +
      fixtures.

## Notes from execution

### Deliverables landed

- `packages/db/src/schema/sets.ts` — table `set` (15 cols, PK + unique
  on `canonical_key`, `(release_date desc, language, code)` index).
- `packages/db/src/schema/cards.ts` — table `card` (20 cols, PK + unique
  on `canonical_key`, FK → `set.id`, `(set_id, number)` btree, GIN
  trigram on `name`).
- `packages/db/src/schema/printings.ts` — table `printing` (13 cols,
  PK + unique on `variant_key`, FK → `card.id`, `card_id` btree,
  partial index `WHERE include_in_master_set = true`).
- `packages/db/src/schema/index.ts` — uncommented the three lines in
  the `T-DL-SCHEMA-CARDS` section. No other section touched.
  `export {};` placeholder left in place per orchestrator contract.
- `packages/db/src/migrations/0000_catalog_tables.sql` — generated by
  drizzle-kit, manually renamed from `0000_zippy_silver_sable.sql` to
  the conventional snake-case summary. Prepended a hand-written
  `CREATE EXTENSION IF NOT EXISTS "pg_trgm"` so the GIN trigram index
  works on a fresh Supabase DB (the local Supabase image does NOT
  enable `pg_trgm` by default — verified via
  `select extname from pg_extension`).
- `packages/db/src/migrations/0001_catalog_rls.sql` — hand-authored
  RLS migration. Enables RLS on all three tables, adds public-read
  policies for `anon` + `authenticated`, revokes the permissive
  default writes Supabase grants by default to those roles, and
  re-grants `SELECT` (anon/auth) + full DML (service_role).
- `packages/db/src/migrations/meta/_journal.json` — entry 0 retagged
  to `0000_catalog_tables`; entry 1 added by hand for
  `0001_catalog_rls` (drizzle's journal format: `{ idx, version,
  when, tag, breakpoints }`).

### Spec-vs-orchestrator resolution

Two intentional deviations from the literal task spec, both at the
orchestrator's explicit instruction:

1. **RLS ships in this task.** Spec § "Out of scope" lists "RLS
   policies (T-DL-RLS-POLICIES)". Orchestrator instructed me to ship
   catalog-table RLS now (`0001_catalog_rls.sql`) since the catalog
   posture is trivially "public-read, service-role-write" (per
   `data-model.md` § RLS) and has no user-table dependencies.
   T-DL-RLS-POLICIES still owns `packages/db/src/migrations/rls/`
   (per `dependencies.yaml`); my hand-authored RLS migration lives
   directly under `migrations/` and does not collide.
2. **Fixtures + fixture test deferred.** Spec deliverables include
   `packages/db/src/fixtures/cards.ts` and a round-trip test.
   Orchestrator restricted owns_paths to `schema/`, `migrations/`,
   and the index barrel — no fixtures path enumerated, and "pin
   nothing new" forbids adding a test runner (vitest/node:test). A
   follow-up task should add the test infra (vitest in
   `packages/db/package.json`) and then author fixtures + the
   round-trip test.

### Other notes

- Migration index numbering: spec calls for `0001_catalog_tables.sql`,
  but `packages/db/README.md` documents that drizzle-kit's first
  output is `0000_*.sql`. Honored the README; catalog migration is
  `0000`, RLS migration is `0001`. If a future schema task assumes
  numbering starts at `0001`, the orchestrator can re-number — the
  journal `tag` field is what binds journal → SQL.
- Export naming: `setTable` / `cardTable` / `printingTable` (plus
  `Set` / `NewSet` / etc. type aliases). The `Table` suffix avoids
  the SQL-keyword collision on `set` and is consistent across the
  three exports. Downstream tasks (T-DL-SCHEMA-COLLECTIONS) should
  import as `import { cardTable, printingTable } from
  '@binderly/db'`.
- Local DB cleanup: dropped my test rows after live verification
  (`select count(*) from set/card/printing` all return 0). Supabase
  stack left running for the orchestrator.
- Parallel-sibling note: `T-DL-SCHEMA-USERS` shares the same local
  Supabase instance (port 54322) since both worktrees default to
  that port. During my live-verification run I observed the
  sibling's `profile`/`subscription` tables appear/disappear in the
  shared `public` schema. To isolate my migrations I dropped the
  sibling tables + the `drizzle` schema once before re-running
  `db:migrate`. The orchestrator should run `pnpm db:reset` after
  merging both branches so the merged migration set applies cleanly
  end-to-end.
